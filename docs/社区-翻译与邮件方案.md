# 社区后续方案：自建机器翻译 + 通知邮件策略（决策已定）

> 记录时间：2026-09-12　决策人：项目负责人
> 状态：**已实施并验证**（见文末「四、落地记录」）

## 一、决策

| 事项 | 决策 |
| --- | --- |
| 机器翻译 | **自建**（不接商业翻译 API）：由运维自托管翻译服务，前端按需调用、译文落缓存 |
| 邮件通知范围 | **仅三类**：① 审核结果 ② 校验类（注册/改密验证码，已有）③ 网站通知（维护/公告等） |
| 网站通知的发送方式 | **由后台 OA 主动群发**（管理员在后台创建并发送），不随社区事件自动发信 |

## 二、实施要点

### 2.1 自建翻译（保留可插拔，不引入商业依赖）

1. **配置项**（`application.yaml` → `app.translate.*`）
   - `provider`：`none`（默认关闭）/ `libretranslate` / `ollama` / `glossary`
   - `base-url`：自托管服务地址（如 `http://127.0.0.1:5000` 或 `http://127.0.0.1:11434`）
   - `api-key`：可选（LibreTranslate 支持）
   - `timeout-seconds`：默认 8；失败即降级为「仅原文」，不阻塞页面
2. **Provider 抽象**：`TranslateProvider` 接口 + 三个实现
   - `LibreTranslateProvider`：`POST {base-url}/translate`，参数 `q/source/target/format=text`
   - `OllamaProvider`：`POST {base-url}/api/generate`，提示词固定为「只输出译文，不要解释」
   - `GlossaryProvider`：内置高频文化词表（民族名/节日名/非遗术语）逐词替换，**零依赖兜底**，即使未部署任何服务也有可用的基础翻译
3. **缓存表**（迁移 `V6__translation.sql`）
   ```
   discussion_translation(
     id, target_type, target_id,   -- topic / post / message / board
     source_locale, target_locale,
     source_hash,                  -- 原文指纹，正文改动即失效
     content, provider, created_at,
     UNIQUE(target_type, target_id, target_locale, source_hash)
   )
   ```
4. **接口**
   - `POST /api/v1/translate` body `{ targetType, targetId, targetLocale }` → 命中缓存直接返回；未命中调用自建服务并写缓存
   - 列表页只翻标题（成本可控）；详情页按需翻正文
   - 响应含 `provider` 字段，前端**必须标注「机器翻译」**并提供「查看原文」切换
5. **UI**：帖子/楼层/私信气泡右上角「译」按钮；`lang` 字段已落库，可直接判定原文语言与是否需要翻译

### 2.2 邮件通知收口

1. **收窄自动发信**：`NotificationServiceImpl.EMAIL_TYPES` 改为仅 `review_result`（审核通过/驳回）。
   - `report_result`（举报处理回执）改为**仅站内**，不发邮件
   - `topic_reply / post_reply / mention / message / follow` 一律**仅站内**
2. **新增后台 OA 公告群发**（网站维护/公告等）
   - `POST /admin/discussion/broadcast` body `{ title, content, email: boolean, audience: all|active, link? }`
     - 权限：`discussion:review`（或新增 `system:broadcast`）
     - 行为：写入 `notification(type=system)` 给目标用户（分页批量插入），`email=true` 时再异步发信
     - 保护：单次收件人上限（如 2000）、`rateLimit` 限流、`discussion_moderation_log` 记审计
   - 后台 UI：治理页新增「站内公告」页签（标题/正文/是否邮件/受众/预览收件人数/发送）
3. **开关**：`app.notify.email-enabled` 由 `false` 调整为 **`true`**（按本次决策），并在文档中注明：开发环境既有的 SMTP 为真实账号，测试时请用真实可收信邮箱或临时关闭该开关。

### 4.2 与原始方案的差异（有意为之）

1. **调用链改为「词表优先 + AI 兜底」**：`provider: glossary` + `fallback-provider: spring-ai`（打包默认）。词表命中后还要过**覆盖率门限** `glossary-min-coverage`（默认 0.8）：只译出几个术语、其余仍是原文时不算数，直接交给 AI，避免展示半截混杂文本；AI 也不可用才 `translated=false` 返回原文。`BASE-URL`/`API-KEY`/`MODEL` 仅 `libretranslate`/`ollama` 通道使用。
2. **新增 `spring-ai` 通道（决定人补充要求）**：机器翻译不必自建 HTTP 客户端，改为复用 `AiConfig` 中已有的 Spring AI `ChatClient`——`AiConfig` 统一装配两个客户端：`chatClient`（通用人格「小夏」，`@Primary`）与 `translateChatClient`（翻译专用系统提示词，两者互不影响）。模型 / `base-url` / `api-key` 全部沿用 `spring.ai.openai.*`，未来新增 AI 用途只需在 `AiConfig` 加客户端。
3. **词表入库 + AI 实时沉淀（迭代 7/8，决定人补充要求）**：
   - 原 `classpath:translate/glossary-zh-en.tsv` 迁到表 `translate_glossary`，后台「翻译词表」页可维护；匹配逻辑与语义不变（CJK 最长匹配 / 拉丁词边界 / 反向自动推导），并新增批量导入导出与试译预览（含覆盖率诊断）。
   - **AI 翻译时顺手把术语沉淀进词表**：`translateChatClient` 的系统提示词要求译文之后附 `---TERMS---` 与「原文术语=译法」列表，后端切分后只把译文返回前端、把术语写回词表（`remark='AI 自动提取'`、只新增不覆盖、术语必须出现在原文里、单次上限 `auto-glossary-max-terms`、可用 `auto-glossary-enabled=false` 关闭）。零额外模型调用，词表随使用自动变准，命中率上升后模型调用自然下降。
4. **前端标注跟着「实际通道」走**：因为同一次浏览里标题可能由词表产出、正文由 AI 产出，`provider` 由后端返回、前端按它显示「机器翻译 · 词表兜底」或「机器翻译 · AI 大模型」（新增 `src/utils/translate.ts`），而不是固定显示配置里的主通道文案。
5. **兜底链**：主通道失败先回退兜底提供方，仍失败才 `translated=false` 仅显示原文；`fallback-provider: none` 可关闭兜底。
6. **`glossary` 的降级语义**：词表一条都没命中、或覆盖率不达门限时视为翻译失败（进入兜底/降级）——避免读者误把词表替换结果当作完整译文。
7. **权限点**：公告群发使用新增的 `system:broadcast`（默认仅 `super_admin`），未复用 `discussion:review`，让「站务公告」与「内容审核」职责分离；翻译词表使用 `translate:glossary`（`super_admin` + `content_admin`）。
8. **`active` 受众**：原先 `last_active_at` 从不更新，本轮在**登录成功时**写入，`active` = 近 30 天有登录记录的未禁用账号。

### 4.3 顺手修掉的三个既有缺陷

1. **正文被写入标题**：`SensitiveWordServiceImpl#check` 一直返回非空 `cleaned`（等于「标题+正文」的检测文本），而 `DiscussionServiceImpl` 用 `check.cleaned() == null ? content : check.cleaned()` 落库 → **所有帖子正文都被写成「标题 + 换行 + 正文」**。已改为：只有 `replace` 级词真正被掩码时才返回 `cleaned`，并由 `maskedBody()` 剥掉标题前缀。
2. **通知邮件污染验证码通道**：通知/公告邮件原先复用 `MailService#sendMail`，会套验证码模板并把通知正文写进 `sys:sms:captcha:{邮箱}`，使 `verifyCode()` 可能被非验证码内容命中。已拆出 `sendHtml`，验证码通道只服务注册/改密。
3. **编辑帖子会丢语言标记**：`updateTopic` 用 `defaultLang(request.lang(), null)`，请求未带 `lang` 时一律回落成 `zh` → **编辑一篇英文帖后它被当成中文**，直接影响翻译方向判断。已改为请求未携带时保留原语言。

### 4.5 运维注意事项

- **迁移**：`V7__translate_glossary.sql` 需要在**所有要跑翻译的环境**执行（本地库与生产库均已执行）。
- 通道选择：默认 `APP_TRANSLATE_PROVIDER=glossary` + `APP_TRANSLATE_FALLBACK=spring-ai`（词表优先、AI 兜底）；`APP_TRANSLATE_FALLBACK=none` 表示不给兜底（宁可只显示原文也不调模型）；`libretranslate`/`ollama` 需配 `APP_TRANSLATE_BASE_URL`；`APP_TRANSLATE_PROVIDER=none` 关闭翻译并让前端自动隐藏「译」按钮。
- **覆盖率门限调优**：`APP_TRANSLATE_MIN_COVERAGE`（默认 0.8）越高越倾向走 AI（质量优先、成本高），越低越倾向用词表（省钱、但可能夹杂原文）。可用后台「试译预览」看具体覆盖率再定；发布前建议拿真实帖子抽样几条看看分流是否符合预期。
- **术语沉淀复核**：AI 沉淀的条目备注为「AI 自动提取」，后台搜索该关键词即可复核，发现不准可直接停用或删除（停用不参与替换但保留记录）。若某段时间不希望自动写入，设 `APP_TRANSLATE_AUTO_GLOSSARY=false`（无需改提示词）。
- **`spring-ai` 通道按次消耗模型额度**：列表页只翻标题、译文按原文指纹缓存、词表命中后就近零成本，是主要成本控制手段；`APP_TRANSLATE_TIMEOUT` 决定单次调用超时后何时转入兜底（本地模型服务可适当放宽，如 40 秒）。
- 词表维护：后台「翻译词表」页（`translate:glossary` 权限）；只有正向 zh→en 词条时反向自动可用，**不要**为同一术语再建一遍反向词条（会让同一语言的词条互相覆盖）；优先录入完整专名（如「那达慕大会」而非「那达慕」）。
- AI 配置集中在 `AiConfig`：新增 AI 用途时在 `AiConfig` 里加 `ChatClient` Bean（系统提示词随之集中管理），业务侧注入使用；通用 `chatClient` 已标 `@Primary`，按类型注入不会因翻译客户端存在而歧义。
- `discussion_translation` 是纯缓存，可随时清空；`cleanup-e2e-data.sql` 已加入「孤儿译文」与测试词条（`E2E%`）清理（**不会**清理「AI 自动提取」的正常沉淀条目）。
- 发信：`APP_NOTIFY_EMAIL_ENABLED`（默认 `true`）；开发环境 SMTP 为真实账号，测试请用可真实收信的邮箱，或临时置 `false`。公告群发受 `APP_NOTIFY_BROADCAST_MAX`（默认 2000）限制。
