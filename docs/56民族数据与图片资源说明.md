## 二、人口数据（2020 年第七次全国人口普查）

- 口径：2020 年 11 月 1 日零时第七次全国人口普查。
- 主来源：《中国人口普查年鉴-2020》表 2-1《全国各民族人口及比重》（国家统计局发布）。
- 校验方法：
  1. 与《第七次全国人口普查公报（第二号）》公布的汉族人口 **1,286,311,334** 人、少数民族合计 **125,467,390** 人核对一致；
  2. 56 个民族人口合计与年鉴表 2-1 合计 **1,409,778,724** 人（含未定族称人口 836,488 人）核对，误差在 OCR 识别误差范围内（±5 万人，集中在人口少于 5 万的小民族）；
  3. 与维基百科/新闻媒体转载的七普分民族数据抽样比对一致（如壮族 19,568,546、回族 11,377,914、满族 10,423,303、苗族 11,067,929 等）。
- 备注：
  - 高山族人口为**大陆地区**统计数据（3,479 人，不含台湾地区）；
  - 数据库中 `population` 字段统一使用 2020 年七普数据；
  - 民族概况文本中引用的「2010 年人口」出自国家民委官网原文（六普口径），仅作历史对比参考。

## 三、民族概况文本（国家民委官网）

- 每个民族抓取 4 个栏目：概况（人口、分布、自称、语言、文字）、历史沿革、风俗文化、发展现状。
- 概况文本源自《民族问题五种丛书》之《中国少数民族》卷（国家民委组织编纂的权威民族志）。
- 数据库 `description`（民族简介）为**数千字长篇**：合并「概况 + 历史沿革 + 风俗文化」三栏目官方全文（约 5,000–16,000 字/族，平均约 11,000 字），并以 `【历史沿革】`、`【风俗文化】` 小节标题分段；风俗文化部分天然涵盖各族**传统节日与饮食习俗**（如哈萨克族「那吾肉孜」新年与奶制品、回族开斋节与盖碗茶等）。
- `summary` 采用概况首段（约 110 字内按句断句）；`description_en`、`summary_en` 为基于官方内容编写的英文版本。
- 前端民族详情页「概况」标签按段落渲染长文：`【…】` 行显示为小节标题（强调底色 + 左侧色条），首段保留首字下沉（dropcap）。
- 除民族主表外，还基于国家民委「风俗文化」栏目与权威资料为每个民族补充了完整的内容矩阵：
  - **民族节日 166 条**（每族约 3 个代表节日，含日期/起源/习俗）
  - **传统艺术 164 项**（每族约 3 项，标注世界/国家/省级非遗级别）
  - **风俗习惯 112 条**（每族 2 条：礼仪/服饰/饮食/信仰等）
  - **民族美食 168 道**（每族 3 道代表美食）
  - **聚居地 112 处**（每族 2 处，含坐标，供「聚居地」地图/时间线展示）
  - 使网站「概况 / 风俗 / 节日 / 艺术」等板块均有真实内容可展示。

## 五、图片资源（Wikimedia Commons）

### 5.1 采集方式
- 通过 Wikimedia Commons API（`generator=categorymembers` + `prop=imageinfo`）按民族分类（如 `Category:Miao`、`Category:Clothing of Tibet`、`Category:Zhuang people` 等）检索，优先「服饰 / 人物 / 传统场景」子分类。
- 筛选条件：JPEG/PNG/WebP、宽 ≥ 900px、高 ≥ 600px、宽高比 0.5~2.2、排除地图/旗帜/徽标/图表等非照片内容。
- 每族下载 2 张候选（`cover.jpg` 主图 + `cover2.jpg` 备选）。

### 5.2 本地化处理与存放架构
- 统一转换为 JPEG，最长边 ≤ 1200px，质量 82%，用于网页展示（懒加载、压缩体积）。
- 共 56 个民族 × 封面图 109 张（其中 53 族含 2 张：`cover.jpg` 主图 + `cover2.jpg` 备选），合计约 31 MB。
- **图片组织原则（业务图片归后端，各端静态资源归各包）**：
  - **业务图片（民族/节日/艺术封面）→ 后端**：`backend/src/main/resources/static/images/ethnic/{slug}/`，由 Spring Boot 从 `classpath:/static` 以 `/images/...` 路径对外提供（`http://localhost:20256/images/ethnic/{slug}/cover.jpg`）；
  - **C 端自有静态资源 → 前端包**：`public/`（favicon、icons、占位图 `public/images/placeholders/placeholder.jpg`）；
  - **后台自有静态资源 → 后台包**：`admin/public/`（logo 等）；
  - 前端包中不再存放业务图片副本（已移除 `public/images/ethnic`、`admin/public/images/ethnic`）。
- **前端访问路径**：数据库 `cover_image` 存相对路径 `/images/ethnic/{slug}/cover.jpg`；
  - 开发环境：C 端与后台的 vite 代理已将 `/images` 转发到后端 `http://localhost:20256`（见 `vite.config.ts`）；
  - 生产环境：Nginx 需将 `/images` 反向代理到后端（与 `/backend-api` 同理），例如
    `location /images { proxy_pass http://localhost:20256; }`。
- **占位图本地化**：原 C 端 `CoverImage` 兜底使用远程 AI 生成图（`coresg-normal.trae.ai` 网络接口），
  现改为本地占位图（`public/images/placeholders/placeholder.jpg`，取材自真实民族照片），
  `src/utils/format.ts` 的 `aiImage()` 已不再请求任何外部图片服务；
  `design/` 目录设计稿中的全部网络图片引用也已下载并替换为本地文件（`design/images/placeholder.jpg`）。

### 5.3 许可说明（重要）
- Wikimedia Commons 仅收录**自由许可**或公有领域作品，主流许可包括 **CC BY / CC BY-SA / CC0 / 公有领域（PD）**，均允许非商业与商业使用，但 **CC BY / CC BY-SA 要求署名**。
- 本毕设仅作**非商业教学展示**；正式答辩展示或上线前，请按各图片的许可要求在页面添加署名（作者 + 许可 + 来源链接）。
- 每张图片的完整授权信息（作者、许可类型、Commons 页面链接、原图链接）已记录在采集清单中：
  - `scripts/scrape/tmp/commons2/manifest.json`（采集原始清单，含 `title / license / artist / page`）
- 若需完全规避署名义务，可仅选用 CC0/公有领域图片，或改用自摄/原创图片。

### 10.1 民族分布地图（A-1）

- **入口**：民族列表页 `/ethnic` 新增「卡片墙 / 分布地图」视图切换。

### 10.2 节日日历与农历换算（A-2）

- **数据现状**：`festival` 表 192 条节日中，只有 **33 条**有 `solar_date`，**159 条**只有农历或民族历法表述。
- **换算实现**：`LunarCalendarUtil`（1900–2100 农历数据表，零依赖）+ `LunarFestivalDateResolver`（文本解析）：
  - **能精确换算**：`农历正月初一`、`农历八月十五`、`农历五月二十九`、`农历闰四月初八`；
  - **区间取起始日**：`农历七月十二日至九月十五日`；
  - **仅到月则估算**：`农历八月`、`农历七八月` → 该月十五，标记 `dateSource=approx`；
  - **不猜日期**：`伊斯兰历十月一日`、`傣历九月十五日`、`藏历…` 一律跳过，避免给出错误日期。
- **精度校验**：用春节 / 中秋 / 端午 / 元宵 / 腊八 / 闰月等已知日期做断言，
  **2020–2026 共 26 项全部通过**（如 2024 春节 = 2024-02-10、2025 中秋 = 2025-10-06、2026 中秋 = 2026-09-25）。
- **接口**：`GET /festivals/calendar?year=`，按月聚合 + 今日节日 + 未来 30 天。
  2026 年 192 条节日中 **101 条**成功落到日历。
- **前端**：节日日历页 `/festival/calendar`（月历网格 + 月份切换 + 年份切换 + 当月列表），
  `approx` 来源以虚线弱化并在列表中显式提示「日期为估算」。

### 11.2 传承人数据补充（本轮数据治理）

`art.inheritors` 是本轮唯一需要**新增数据**的部分。

**数据来源（权威、可反查）**：文化和旅游部公布的《国家级非物质文化遗产代表性项目代表性传承人》
**第 1–6 批完整名单**，共 **4001 条**记录（第一批 226 / 第二批 547 / 第三批 706 / 第四批 498 /
第五批 1082 / 第六批 942），从官方 `.doc` / `.xls` / `.docx` 附件解析为结构化表后，
按项目名与库中 144 个缺失项逐一匹配。

**补充原则**：

- **只填官方名单中确实存在的姓名**，不做任何推测或凭印象填写；
  每一处填入都可回溯到官方名单中的「批次 / 项目 / 地区」。
- **宁缺毋滥**：官方未公布个人传承人的项目一律保持 `[]`。
- **区分项目类型**：技艺类 / 表演类 / 史诗类多有明确传承人；
  而「XX族服饰」类官方**以群体或地区为单位**保护，通常不设个人传承人，此类保持为空。

**补充结果**：

| 级别 | 项目数 | 有传承人 | 覆盖率 |
| --- | --- | --- | --- |
| 世界级 | 16 | **16** | **100%** |
| 国家级 | 149 | 93 | 62% |
| 合计 | 165 | **109** | **由 13% 提升至 66%** |

仍为空的 56 项中，**17 项为服饰类**（官方未设个人传承人），其余分布在手工艺 16、音乐 12、舞蹈 9、戏剧 2。

**迁移脚本**（幂等，可重复执行）：

- `V8__art_inheritors.sql` —— 补充 88 项传承人（仅当该行 `inheritors` 为空时才写入，
  不覆盖后续人工维护），实测重复执行更新 0 行。
- `V9__fix_art_inheritors.sql` —— 见下条数据质量修正。

**数据质量修正（V9）**：原库中「藏戏」的传承人记录为 `觉木隆`，但**「觉木隆」是藏戏演出团体名**
（拉萨觉木隆藏戏队），并非传承人姓名 —— 把团体名当作个人传承人展示会造成事实性错误。
依据官方第六批名单「藏戏（拉萨觉木隆）」条目，已修正为真实传承人 **边点旺久、洛桑扎西**。

> **答辩提示**：传承人数据是「可溯源」的强证据 —— 说明数据来源、批次与匹配方法，
> 并主动说明**为何有 56 项为空**（官方不设个人传承人 / 官方名录中无该项目），
> 比声称「全部收录」更能体现数据治理的严谨性。

### 11.4 文化专题：民族服饰与民居建筑（B-1 / B-2）

**核心思路：跨表合流，不新增内容表。** 这两个主题的内容**早已存在于库中，只是分散在两处**：

| `art` | costume 25 项、architecture 3 项 | **非遗级别 + 专属配图** | 分别只覆盖 25 / 3 个民族 |

两者按**民族**合流后正好互补：`custom` 出内容、`art` 出配图与名录属性。

**实测结果**：

| 专题 | 涉及民族 | 条目数 | 其中非遗项 | 有配图民族 |
| --- | --- | --- | --- | --- |
| 民族服饰 `/culture/costume` | 40 | 57 | 25 | 40（100%） |
| 民居建筑 `/culture/dwelling` | 14 | 16 | 3 | 14（100%） |

**分类维度**（服务端按内容关键词推导，非库中粗分类）：

- **服饰 · 工艺技法**：刺绣 9 / 银饰 6 / 其他 6 / 织锦 4 / 印染 3 / 编织 2 / 皮毛工艺 2
- **民居 · 建筑形制**：干栏式 3 / 穹庐式 3 / 庭院式 3 / 碉楼碉房 2 / 木构 1 / 宗教建筑 1

> **数据治理提示（真实踩过的坑）**：`ethnic_custom.category` 只有「服饰」「居住」「建筑」这类粗分类。
> 早期实现里**分类统计**按关键词规则推导（刺绣、银饰…），**条目**却仍沿用库中的「服饰」，
> 结果前端点击「刺绣（9）」筛出 **0 条** —— 统计与条目口径不一致。

> 这是「同一份数据在多处派生时必须同源」的典型案例，答辩时也可作为数据一致性处理的说明。

### 11.5 人物专栏（B-7）

**数据基础**：B-7 **不需要新增任何人物内容** —— V8 补充的 `art.inheritors`

**新增表 `person_profile`**（迁移 `V10__person_profile.sql`）：承载角色类型 / 领域 / 简介 / 生卒年，
以 **`(person_name, ethnic_group_name)`** 与 `art` 关联。

> **关联键为何必须含民族**：库中确实存在**同名不同族**的情况 ——
> 「马金山」同时是**回族花儿**（世界级）与**东乡族花儿**（国家级）的代表性传承人。

#### 11.5.1 角色区分（本轮的数据治理重点）

| --- | --- | --- |

#### 11.5.2 专栏口径

- **人物数 163 人 / 条目 164 条** —— 差额来自「马金山」同名不同族的两个人，各自成条，属预期行为。

## 十二、后台可维护性（B 系列接入管理端）

方向 B 新增的四张内容表此前**只有 C 端展示接口**，后台无法维护 ——
一旦需要订正数据（如补录某位传承人的简介、修正自治地方成立年份），只能直接改数据库。
本轮补齐了这一环。

### 12.1 侧边栏按业务域分组

原先后台也是平铺菜单，且混用了「表名」与「部门」两种命名口径
（「民族管理」「审核管理」「讨论区治理」「翻译词表」）。
现改为**按业务域分组**，让使用者按「我要做什么」而非「数据在哪张表」找入口：

| 分组 | 包含 |
| --- | --- |
| **工作台** | 数据概览 |
| **内容运营** | 民族、节日、艺术、专题、**人物档案**、**自治地方**、**传统体育**、表单配置 |
| **社区治理** | 讨论区、内容审核 |
| **系统设置** | 用户管理、角色权限、翻译词表 |

分组与组内条目**都按角色过滤**，过滤后为空的分组整体隐藏，不出现空分组。

### 12.2 三张新表的完整 CRUD

| 资源 | 权限点 | 业务唯一键 |
| --- | --- | --- |
| 人物档案 `person_profile` | `person:list/create/update/delete` | **姓名 + 民族** |
| 民族自治地方 `autonomous_area` | `area:list/create/update/delete` | 名称 |
| 传统体育 `traditional_sport` | `sport:list/create/update/delete` | 名称 |

共新增 **12 个权限点**；`content_admin` 获得全部，`editor` 获得只读 + 编辑（无增删）。

**人物档案的唯一键含民族**这一点尤其重要：库中确实存在同名不同族的人物
（「马金山」同属回族花儿与东乡族花儿），若唯一键只取姓名，后台编辑时会错误地
把两个人当成同一条记录处理。

### 12.3 实现中发现并修复的两个缺陷

这两处都是**端到端测试跑出来**的，不是靠人眼检查发现：

1. **jsonb 数组字段无法接收请求体**（表现为新增/编辑自治地方与体育项目全部报 `1001 参数错误`）。
   原因：`ethnic_groups` / `ethnic_origins` / `sub_events` 是 jsonb 列，实体中以
   **JSON 文本（String）** 承载；直接用实体接请求体时，前端传来的 JSON 数组无法写入 String 字段。
   **修复**：这两类资源改用 DTO（字段为 `List<String>`），由服务层序列化后写入实体 ——
   与既有 `DiscussionServiceImpl` 处理 `images` 数组的做法保持一致。
2. **删除全部报 `5000 服务器内部错误`**。原因：EasyQuery **默认禁止物理删除**（防误删），
   删除链路需显式调用 `.allowDeleteStatement(true)`。**修复**：三处删除均显式放行。

修复后用端到端脚本回归，**33 项断言全部通过**，覆盖：增删改查、唯一键冲突（`2001`）、
同名不同族允许新增、按关键词/级别/类别筛选、未登录拦截（`1003`）、非法 ID（`1001`）、
以及测试数据清理后的数量校验。

## 十三、内容可溯源（方向 C-1）

## 十四、图片版权署名（方向 C-4）

### 14.1 必须正视的问题：原始版权元数据已丢失

在设计署名功能时排查发现，**无法把现有图片对应回它的来源页**：

| 事实 | 后果 |
| --- | --- |
| 图片采集后被统一重命名为 `cover.webp` / `{slug}.webp` | 原始 Commons 文件名丢失 |
| 采集清单 `scripts/scrape/tmp/commons2/manifest.json` 所在的 `scripts/` 目录已不在仓库中 | 作者 / 许可 / 来源页记录丢失 |
| `media_asset` 表 0 行 | 数据库中亦无原图链接 |
| 文档仅记录「民族图取自 Commons」，food 记为「百度图搜来源，毕设展示用」，festival/art 未记录来源 | 目录级背景，非逐图署名 |

**因此不可能凭空生成正确的逐图署名。** 编造作者与许可比留白危害更大 ——
那会让「已署名」变成假的，反而掩盖了真实的合规缺口。

### 14.2 处理方式：如实分类，不编造

新增表 `image_credit`（迁移 `V14__image_credit.sql`），核心是 **`credit_status`** 三态：

| 状态 | 含义 | 当前数量 |
| --- | --- | --- |
| `verified` | 已核实（有作者与许可） | **0** |
| `unverified` | **来源待核** | **574** |
| `original` | 原创或无需署名 | 0 |

**574 张图片全部登记为 `unverified`**，并在备注中如实写明各目录的来源背景。
服务层有一道硬性约束：**标为 `verified` 时至少需填作者或许可**，否则拒绝保存 ——
防止把「待核」伪装成「已完成」。

### 14.3 页面呈现（两处）

1. **图片角标**（`components/ImageCreditBadge.vue`）：
   挂在图片右下角的小圆标，hover / 点击展开完整署名面板。
   - 已核实 → 显示 `©`，面板给出「作者 / 许可」与许可条款、来源页链接；
   - 未核实 → 显示 `?`，面板明确写「**来源待核**」并说明原因。
2. **详情页「图片来源」汇总区**（`components/ImageCredits.vue`）：
   列出本页每张图的说明、来源站点与核实状态，并在底部如实交代整体进度：
   「站内共 574 张图片，已核实 0 张（0%），待核 574 张；CC BY / CC BY-SA 要求署名，
   当前仍有 574 张需署名但尚未核实来源。」

> 与「参考资料」（C-1）**分工明确**：C-1 讲**文字数据**的出处（民族志 / 普查 / 非遗名录），
> C-4 讲**图片**的来源与许可。

### 14.4 补齐路径（可执行，非空谈）

署名不是「实现不了」，而是「需要逐张核实」。为此提供了完整闭环：

| 工具 | 作用 |
| --- | --- |
| `scripts/backfill-image-credits/generate-with-owners.cjs` | 扫描实际图片 + 数据库引用，生成带**可读说明**（如「阿昌族民歌 · 配图」）的署名记录 |
| `scripts/backfill-image-credits/export-pending.cjs` | 导出**待核清单** `docs/图片署名待核清单.csv`（574 条，Excel 可直接打开） |
| 后台「系统设置 → 图片署名」 | 逐张录入作者 / 许可 / 来源链接；可按「只看待核」筛出未完成项 |

**核实方式**：用 Wikimedia Commons 的反向图片搜索按图找回来源页，把作者、许可、来源链接填入后台，
状态改为「已核实」后，C 端**自动**显示真实署名，进度统计随之更新。

**实测**：端到端脚本 **23 项断言全部通过**，覆盖进度统计、按内容/按路径查询、
未核实时不生成署名文本（`creditLine` 为 null）、后台核实全流程（含「假核实」被拒）、
核实后公开接口正确读取、以及还原为待核后进度回落。

## 十五、历史沿革结构化（方向 C-2）

### 15.1 先说结论：这批数据不是「年表」

56 个民族的 `ethnic_group.description` 中，`【历史沿革】` 小节**每行恰好出现一次**
（与 `【风俗文化】` 合计 114 次 = 56 × 2），内容是**编年体散文**，不是结构化的年份条目。
实测（1,121 段）：

| 度量 | 结果 | 含义 |
| --- | --- | --- |
| 段落总数 | 1,121（中位 19 段/民族，最多 41 段） | 单篇最长 10,605 字 |
| 段落按时间排序 | **仅 10 / 56 行** | 蒙古族 1279→1771→1776→1946→**1607**→1859；苗族 1502→1840→**1349** |
| 完全无时间锚点的段落 | **346 段（31%）** | 藏族的「差巴/堆穷/朗生」农奴等级、蒙古族的「畜牧业经济部门」 |
| 含具体年份 | 990 处 | 如「1206年」「651年」「763年」 |
| 仅世纪表述 | 303 处 | 「13世纪初」「公元3世纪」 |
| 仅朝代表述 | 846 处 | 「唐宋时」「秦汉时代」「殷周时代」 |

段落是**专题式**（族源考证 / 迁徙 / 社会形态 / 内部组织），而非时间线——
苗族的最后两段讲的是「议榔」「理老」这类**社会组织制度**，本就没有年份。

**因此不把它做成「年份→事件」的年表**：那需要把「13世纪初」折算成具体年份，
属于推断编造，与本项目一贯的「不编造」原则冲突。

### 15.2 实际做法：只做可验证的结构化

`EthnicHistoryParser`（纯函数、无 IO）把该小节拆成三部分：

| 输出 | 收录规则 |
| --- | --- |
| `timeline` 时间轴 | **仅**收录原文明写出具体年份（3~4 位数字 + 「年」）的段落；年份与原文措辞原样保留 |
| `eras` 时代分期 | 按原文自述的朝代/时代词归入 9 个时代，**按时间先后排序**（先秦→秦汉→魏晋南北朝→隋唐五代→宋辽金西夏→元代→明代→清代→近现代） |
| `paragraphs` 段落索引 | 全部段落，标注命中的时代与首个明确年份；无锚点的标注为「专题叙述」 |

**关键约束**：不做年份归一化（「13世纪初」不进时间轴）、不改写正文、不截断段落。

### 15.3 实测覆盖（真实 56 行数据）

| 指标 | 结果 |
| --- | --- |
| 断言 | **1,460 条全部通过** |
| 解析段落 | 1,121 |
| 时间轴条目 | 420（每个年份写法都验证确实存在于其来源段落中） |
| 含时间轴的民族 | **54 / 56** |
| 无时间轴的民族 | 普米族、乌孜别克族（原文只有时代表述、无具体年份）——仍可看「时代分期」，页面自动落在该视图而非空白 |

断言覆盖：年份写法必须能在原文中检索到、段落下标与段落文本一致、时代下标不越界、
计数与列表长度一致、`anchoredRatio` 区间合法、**时代按时间先后排列**（回归守卫）、
`year` 与 `yearText` 一致（公元前为负），以及 null / 无标记输入返回空结构。

### 15.4 页面呈现

「历史沿革」标签页顶部提供三个视图切换 + 一行**如实说明**：

> 共 27 段，其中 22% 含明确年份（6 条）已列入时间轴；其余为族源、社会形态等专题叙述，收在「全文索引」。

- **时间轴**：按原文顺序列出带年份的段落，长段落可展开全文；
- **时代分期**：按 9 个时代分组，点击段落可跳转并在全文索引中定位；
- **全文索引**：全部段落，带段落号、年份与时代标签。

英文语境下该视图自动隐藏（时间轴与朝代词均由中文原文解析而来），回退为按英文正文分段的图文阅读。

### 15.5 顺带修复的问题

- **时代排序错乱**：最初按「首次出现顺序」遍历 `LinkedHashMap` 输出，
  得到「先秦→秦汉→清代→近现代→魏晋南北朝」这类乱序；改为**按时代词表固定顺序**输出，
  并补上回归断言，防止再次退化。
- **CSS 类名冲突**：时间轴条目用的 `.tl-item` 与既有「聚居地」模块的 `.tl-item` 同名，

  （该冲突由 UI 断言 `timeline 条目数 == 接口返回数` 发现。）

### 16.4 实现中发现并修复的缺陷

本轮一共暴露并修复了 **4 个缺陷**，其中 3 个是既有代码里的潜在问题，由本次数据回填与页面联调触发。

**① `limit` 语义错误导致批次空转（回填服务）**

首版实现里 `limit` 限制的是**遍历行数**，而遍历时已译行只计入 `skipped` 不消耗翻译——
结果每批 20 行配额全被前排已译行吃掉，批次宣称「nothing left to do」，但待译数仍有 148 行。

表现为：festival 译完 41 行后停滞、art 译完 38 行后停滞，进度**永久卡住**。
修复为按**实际调用翻译通道的条数**计数后，单批 `limit=10` 实测待译数 148 → 138 正常推进。
运行脚本的结束条件也从「本批 translated=0」改为「**待译数是否为 0**」，
因为批次内出现 `skipped` 属正常现象，不能据此判定结束。

**② `Food` 实体缺少主键标注 → food 表英文正文全部回填失败**

`Food.id` 未标注 `@Column(primaryKey = true)`（`Festival` / `Art` 都有）。EasyQuery 无法据此生成 WHERE 条件，
报 `entity:Food not found primary key properties`，**168 行 food 全部失败**（festival / art 正常）。
这是个既有潜在缺陷：food 表任何「按 id 更新」的写法都会踩到，只是此前没有代码路径触发它。
补上主键标注后，food 回填立即恢复（首批 25/25 成功、0 失败）。

**③ 语言切换后 `<html lang>` 未同步（刷新即丢失）**

`lang` store 从 `localStorage` 恢复了语言，但只有 `apply()`（用户主动切换时）才会写 `document.documentElement.lang`，
**启动路径上没有调用**。因此刷新页面后 store 里是英文、`<html lang>` 却一直是 `zh-CN`——
既影响无障碍朗读与搜索引擎判断语种，也让「当前是否英文」在不同地方出现不一致判据。
已在 store 初始化时补齐一次同步。

**④ `MachineTranslationNotice` 的 `active` prop 判据错误（Vue Boolean prop 陷阱）**

首版把 `active` 定义为可选 Boolean 并写 `props.active !== false`。
但 **Vue 中缺省的 Boolean prop 会被强制转为 `false`（不是 `undefined`）**，
于是调用方不传该 prop 时条件恒为假，提示**永远不出现**（联调时实测 `source="machine"`、`isEn=true`，`visible` 仍为 false）。
改为要求调用方**显式传入** `active`（由页面计算「确实在展示英文正文」），既不依赖隐式默认值，
也顺带修掉了「有译文但当前显示中文时误报机器翻译」的问题。

### 16.5 页面呈现

`festival` / `art` / `food` 详情页正文在英文语境下优先显示 `descriptionEn`，
无译文时**回退中文**（不会出现空白）。接口 `descriptionEn` / `descriptionEnSource`
随 `FestivalQueryInfoResource` / `ArtQueryInfoResource` / `FoodDetailResource` 一并返回。

英文语境下正文上方显示一行来源提示（`MachineTranslationNotice`）：机器译文标「MT 本页英文由机器翻译生成，仅供参考」，
人工校对的则不提示。**只在确实展示英文正文时出现**，中文阅读时不会误报。

**实测**：C-3 页面端到端 **7 项断言全部通过**，覆盖两种语境下的 `html lang`、
正文语言、译文是否渲染、提示的显示与隐藏，以及 0 控制台错误。

### 16.6 如何继续补齐 / 复核

| 操作 | 方式 |
| --- | --- |

## 十七、全文检索与个性化推荐（方向 D）

### 17.1 先说清楚：环境不允许上 Elasticsearch

改造前先做可行性核查，结论直接决定了技术选型：

| 核查项 | 结果 |
| --- | --- |
| Docker / Podman | **均未安装**（`docker` / `podman` / `nerdctl` 全部 NOT FOUND） |
| 搜索引擎进程 | 9200 / 7700 / 8983 端口**均无监听** |
| PostgreSQL 扩展 | **`pg_trgm` 已安装**（1.6）；`unaccent` / `zhparser` 未安装 |

因此在**不引入新外部依赖**的前提下，采用 **PostgreSQL 原生方案**。
（同时保留了将来切换的余地：检索入口收敛在 `FullTextSearchService` 一个接口上。）

### 17.2 检索覆盖面的真实缺口

改造前的搜索**只覆盖 3 类内容**，而站内实际有 8 类：

| 内容类型 | 条数 | 改造前可搜 |
| --- | --- | --- |
| 风俗习惯 `custom` | 222 | ❌ |
| 节日 `festival` | 192 | ✅ |
| 美食 `food` | 168 | ❌ |
| 艺术 `art` | 165 | ✅ |
| 人物 `person` | 164 | ❌ |
| 自治地方 `area` | 155 | ❌ |
| 民族 `ethnic` | 56 | ✅ |
| 传统体育 `sport` | 20 | ❌ |
| **合计** | **1142** | **仅 413（36%）** |

即 **64% 的内容此前完全搜不到**。本次以 `search_document` 宽表把 8 类内容全部纳入索引
（实测重建 **1142 条 / 约 1.0 秒**）。

### 17.3 实测驱动的一个关键发现：pg_trgm 对中文很弱

如果直接「用 trigram 做模糊搜索」，会遇到中文场景下的严重漏召回。实测数据：

```sql
SELECT similarity('维吾尔族','维吾尔');  -- 0.5
SELECT similarity(name,'蒙古') FROM ethnic_group;  -- 蒙古族 0.4，其余全为 0
```

两字中文输入的相似度**普遍为 0**，默认阈值 0.3 会让绝大多数查询直接漏召回；
即使把阈值降到 0.15，`蒙古` 仍只召回 1 条。

**因此检索改为三路并用**，而不是单靠 trigram：

| 召回方式 | 作用 | 实测表现 |
| --- | --- | --- |
| 子串匹配 `LIKE` | **中文检索主力** | `蒙古` → 56 条 |
| 拼音（全拼 + 首字母） | 拼音输入习惯 | `mengguzu` → 10 条；`mgz` → 1 条（蒙古族） |
| trigram 相似度 | 错别字 / 近似写法补充 | 阈值降至 0.2 参与打分 |

### 17.4 拼音维度：为什么要有「首字母」，以及它为什么只能当辅助

站内原本**只有 `ethnic_group.pinyin` 一列**（且只有 56 个民族有，形如 `Mengguzu`），
其余 7 类内容没有任何拼音字段，也**没有首字母缩写**——用户输入 `mgz` 时搜不到「蒙古族」（实测确认）。

因此引入 `pinyin4j`（体积极小、无外部依赖），在**建立索引时**为每类内容生成两种形式：
全拼 `mengguzu` 与首字母 `mgz`，检索阶段直接匹配拼音列，不做实时转换。

**首字母只能作低权重信号**——实测 56 个民族里有 **6 组冲突**：

| 缩写 | 冲突民族 |
| --- | --- |
| `hz` | 汉族 / 回族 |
| `mz` | 苗族 / 满族 |
| `zz` | 藏族 / 壮族 |
| `yz` | 彝族 / 瑶族 |
| `dz` | 侗族 / 傣族 |
| `sz` | 畲族 / 水族 |

所以打分权重刻意做成 **拼音精确 55 > 前缀 40 > 包含 30 > 首字母 20**。

### 17.5 排序：两个由实测暴露并修复的排序缺陷

初版打分上线后，用真实查询验证时发现两处明显错误：

**① 拼音检索把自治县排到了民族前面**

`mengguzu` 查询下，「蒙古族」与「河南蒙古族自治县」**同为 34.0 分**，
导致真正的目标排到了第 5 位。原因：`pinyin_full LIKE '%mengguzu%'` 对所有**包含**该串的行给同一分数，
而「蒙古族」的 `pinyin_full` 恰好**等于** `mengguzu`（完全匹配）却被同等对待。
修复：拆分为 精确 / 前缀 / 包含 三档。
修复后「蒙古族」128.9 分**稳居第 1**，自治县 34.0 分排在其后。

**② 英文检索全部同分**

`mongolian` 查询下 4 条结果**全部 38.9 分**。原因同上是「包含」与「完全匹配」不分：
「蒙古族」的 `title_en` 恰为 `Mongolian`，其余是 `Khoomei (Mongolian Throat Singing)` 这类**括注包含**。
修复：英文拆为 完全匹配 45 / 子串 35，并新增 `titleEn` 命中方式标识。
修复后「蒙古族」83.9 分第 1，其余 38.9 分。

### 17.6 推荐引擎：真实实现 + 如实标注可信度

**必须先摊开的事实**：改造前站内的行为数据几乎为空。

| 指标 | 数值 |
| --- | --- |
| 用户数 | **5** |
| `view_counter`（浏览量计数） | 23 |
| `like_record` | 6 |
| `favorite` | 3 |
| 兴趣标签表 | **不存在** |

且这些表都是**聚合计数**，无法回答「谁在何时看了什么」，因而**无法据此构建个人画像**。
在这样的量级下，经典 User-CF 完全不可用（任意两用户的共同物品几乎为 0）。

**因此做了三件事：**

1. **新建行为明细表 `user_behavior`**（记录 user + action + target + time），
   并在内容详情页埋点上报——这是能真正积累起来的隐式信号；
2. **新建兴趣标签体系**（`interest_tag` + `user_interest`）作为**显式信号**，
   这是冷启动的解法：新用户没有行为时，勾选兴趣即可获得有意义的推荐；
3. **接口如实暴露依据与样本量**（`basis` / `basisLabel` / `dataNote` / `confidence`），
   不把「热度推荐」包装成「为你推荐」。

**四路召回 + 加权融合**（按可用信号自动降级）：

| 召回路径 | 信号类型 | 权重 |
| --- | --- | --- |
| 兴趣标签 | 显式 | 民族 +50 / 地域 +25 / 主题 +20 / 类型 +10 |
| 行为协同 | 隐式 | 兴趣民族 +30 / 兴趣分类 +12（并**排除已读内容**） |
| 内容相似 | 特征 | 以民族/分类为特征 |
| 热度兜底 | 全局 | `min(popularity,100)×0.1` + 时效最多 +5 + 民族 +3 |

### 17.7 兴趣标签全部由真实数据推导

111 个标签**没有一个是凭空编的分类**，全部取自库中实际数据：

| 维度 | 数量 | 来源 |
| --- | --- | --- |
| `ethnic` 民族 | 56 | `ethnic_group.name`（含主题色与英文名） |
| `region` 地域 | 27 | `ethnic_group.region`（jsonb 数组展开去重；已排除「全国各省区市」这类聚合表述） |
| `topic` 主题 | 20 | 各表实际取值：艺术类别 / 节日类型 / 体育类别 / 非遗级别 |
| `type` 内容类型 | 8 | 与 `search_document.doc_type` 一致 |

### 17.9 实现中发现并修复的缺陷

**浏览埋点在 `onMounted` 里读不到 ID**：`useViewTracking` 初版在 `onMounted` 中读取 `detail.value?.id`，
但详情是**异步加载**的，挂载时 ID 仍为 `null`，导致上报**永远落空**（实测 0 条请求）。
此外调用位置写在 `detail` 声明之前，还构成暂时性死区。
修复：改用 `watch(getId, ..., { immediate: true })` 并在拿到 ID 后只上报一次，
同时把调用位置移到 `detail` 声明之后。修复后实测浏览器打开详情页 → `user_behavior` **+1 条**。

**排查中的两个假象（非代码缺陷）**：
- 用 `127.0.0.1:5173` 访问时请求被浏览器拦截——后端 CORS 白名单是 `localhost:5173`，
  **两者属不同源**；且开发环境实际走 Vite 的 `/backend-api` 代理，不跨域。
- 页面内手动 `fetch` 直连 `:20256` 返回 403，同样是跨域所致；服务端直接调用该接口 `code=0` 正常。
